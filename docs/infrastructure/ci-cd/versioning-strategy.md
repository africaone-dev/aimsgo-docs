# План: Исправление версионирования в CI/CD

## Проблема

Текущая система CI/CD для aims и aims-core имеет критическую проблему с версионированием:

**Текущее поведение:**
1. `build-frontend.yml` запускается при изменении `frontend/**` → создает версию 1.0.1
2. `build-backend.yml` запускается при изменении `backend/**` → создает версию 1.0.2
3. В Helm chart сохраняется только последняя версия (1.0.2)
4. **Результат:** Frontend и Backend имеют разные версии, но Helm пытается использовать одну версию для обоих!

**Почему это проблема:**
- Frontend образ: `aims-frontend:1.0.1` ✅ собран
- Backend образ: `aims-backend:1.0.2` ✅ собран
- Helm chart указывает версию `1.0.2` для обоих
- При деплое Kubernetes пытается использовать:
  - `aims-frontend:1.0.2` ❌ не существует!
  - `aims-backend:1.0.2` ✅ существует

## Правильный подход

Frontend и Backend одного приложения должны **всегда иметь одинаковую версию**:
- `aims-frontend:1.0.1` + `aims-backend:1.0.1`
- `aims-core-frontend:2.3.5` + `aims-core-backend:2.3.5`

## Решения

### Вариант 1: Единый workflow для Frontend + Backend (Рекомендуется)

**Преимущества:**
- ✅ Гарантированно одна версия для FE и BE
- ✅ Атомарный деплой обеих частей
- ✅ Helm chart обновляется один раз

**Недостатки:**
- ❌ Оба образа пересобираются даже при изменении только одного
- ❌ Более долгий CI/CD pipeline

**Реализация:**
- Создать новый workflow `build-and-deploy.yml`
- Триггеры: изменения в `frontend/**` ИЛИ `backend/**` ИЛИ `.github/workflows/build-and-deploy.yml`
- Шаги:
  1. Генерировать одну версию
  2. Собрать aims-frontend с этой версией
  3. Собрать aims-backend с этой версией
  4. Один раз обновить Helm chart с этой версией

### Вариант 2: Разные workflows + координация версий

**Преимущества:**
- ✅ Быстрее - собирается только то, что изменилось
- ✅ Оптимальное использование ресурсов

**Недостатки:**
- ❌ Сложнее логика
- ❌ Нужна координация между workflows

**Реализация:**
- Модифицировать extract-version action:
  - НЕ инкрементировать версию автоматически
  - Использовать текущую версию из Helm chart
  - Собирать образ с существующей версией
- Создать отдельный workflow `bump-version.yml`:
  - Запускается вручную или по расписанию
  - Инкрементирует версию в Helm chart
  - Триггерит сборку обоих образов с новой версией

### Вариант 3: Использовать Git SHA вместо semver

**Преимущества:**
- ✅ Каждый коммит = уникальная версия
- ✅ Точное соответствие кода и образа

**Недостатки:**
- ❌ Нет семантического версионирования
- ❌ Сложно отследить мажорные/минорные изменения

**Реализация:**
- Frontend и Backend используют одинаковый git SHA как версию
- Например: `aims-frontend:a3b2c1d`, `aims-backend:a3b2c1d`

## Рекомендация

**Вариант 1** (Единый workflow) - самый надежный для production:
- Гарантирует консистентность версий
- Простая логика
- Helm chart всегда в sync с образами
